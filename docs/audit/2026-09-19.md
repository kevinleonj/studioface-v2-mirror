## E1 — `/internal/budget` is unauthenticated (critical, worse than reported)

The review reported HTTP 500. It is **HTTP 200**:

```
$ curl -X POST https://studioface.app/internal/budget -H "Content-Type: application/json" -d '{}'
HTTP 200
{"killswitch":false}
```

The 500 the reviewer saw was an empty body failing `await request.json()`. With a
well-formed body the request succeeds and the handler runs.

`app/main.py:338-349`:

```python
def _register_budget(app: FastAPI, d: Deps) -> None:
    @app.post("/internal/budget")
    async def budget(request: Request):
        """Pub/Sub push from the Cloud Billing budget. Flips the kill switch at 100%.
        Cloud Run verifies the OIDC token before this handler runs (push auth)."""
        body = await request.json()
        raw = base64.b64decode(body.get("message", {}).get("data", "")).decode() or "{}"
        note = json.loads(raw)
        if float(note.get("alertThresholdExceeded", 0)) >= 1.0:
            d.pipeline.store.killswitch = True
        return {"killswitch": d.pipeline.store.killswitch}
```

**Root cause.** The docstring asserts "Cloud Run verifies the OIDC token before this
handler runs". The service is publicly invocable — every other route is reachable
anonymously, which is the same ingress — so nothing verifies anything. The handler has no
credential check of its own.

**What it permits.** The code path sets `killswitch = True` when
`alertThresholdExceeded >= 1.0`. The kill switch closes `/api/checkout` and `/api/preview`
with 503. So an unauthenticated caller can take the funnel down.

**NOT TESTED (would change production state).** I did not send a body that flips the
switch; that would take the live service down to prove a point. The read above is enough:
the handler is reached, and the branch is three lines further on.

**Fix.** Verify the Pub/Sub OIDC token in the handler before parsing the body, per R3.

## E2 — `/api/gracias` hands a valid gallery token to anyone (critical)

```
$ curl -i "https://studioface.app/api/gracias?session_id=cs_test_fake"
HTTP/1.1 302 Found
location: https://studioface.app/g/?o=cs_test_fake&t=REDACTED
```

Deterministic — two calls, same token:

```
location: https://studioface.app/g/?o=cs_test_fake&t=REDACTED
location: https://studioface.app/g/?o=cs_test_fake&t=REDACTED
```

`app/main.py:293-303`:

```python
    @app.get(THANKS_PATH)
    def gracias(session_id: str = ""):
        if not session_id.startswith(SESSION_ID_PREFIX):
            raise HTTPException(404)
        token = delivery_token(session_id, d.pipeline.secret)
        return RedirectResponse(f"{GALLERY_BASE}?o={session_id}&t={token}", status_code=302)
```

**Root cause.** The only check is the three-character prefix `cs_`. Stripe is never asked
whether the session exists or was paid, so the HMAC is computed over an attacker-chosen
string and handed back.

**Why it matters beyond this endpoint.** `delivery_token` is the same token that gates
`/api/orders`. This route is a token-minting oracle for the entire order namespace: supply
an id, receive its token. It does not currently expose another customer's photographs —
`/api/orders` only returns image URLs when `status == "delivered"`, and guessing a real
Stripe session id is impractical — but the token that would unlock them is free.

**Fix.** Retrieve the session from Stripe and redirect only when it exists and the paid
condition (R1) holds; otherwise 404.

## E3 — a gallery for an order that does not exist (high)

```
$ curl "https://studioface.app/api/orders/cs_test_fake/44daae73dc96b181d5a7ff2cfc5af963"
HTTP 200 {"status":"pending","images":[]}

$ curl "https://studioface.app/api/orders/cs_test_fake/deadbeef..."
HTTP 404 {"detail":"Not Found"}
```

`app/main.py:318-331`:

```python
    @app.get("/api/orders/{order_id}/{token}")
    def status(order_id: str, token: str):
        if not hmac.compare_digest(token, delivery_token(order_id, d.pipeline.secret)):
            raise HTTPException(404)
        order = d.pipeline.store.get(order_id)
        if order is None:
            # Stripe redirects the browser before it delivers the webhook, so for a few
            # seconds a good link points at an order that does not exist yet. 404 is the
            # signal for a forged link and it stops the poller for good.
            return {"status": "pending", "images": []}
```

**Root cause.** The token check passes (E2 hands out valid tokens) and a missing order is
deliberately reported as `pending`.

**The comment is describing a real problem**, and it is why this needs care rather than a
one-line change: Stripe redirects the browser before it delivers the webhook, so for a few
seconds a genuine paying customer's link points at an order that does not exist. Making
this 404 unconditionally reintroduces "Este enlace no es válido" for real buyers — a bug
this repository has already fixed once.

**Fix.** Fix E2 first, then have `/api/gracias` record the verified order at redirect time
so the race window closes, and only then make a missing order a 404.

## E5 — the CSP is missing hosts Google requires (medium, wider than reported)

Served today:

```
script-src  'self' 'unsafe-inline' https://challenges.cloudflare.com https://www.googletagmanager.com
img-src     'self' data: https://challenges.cloudflare.com https://storage.googleapis.com
connect-src 'self' https://challenges.cloudflare.com https://*.challenges.cloudflare.com
            https://*.google-analytics.com https://*.analytics.google.com
frame-src   https://challenges.cloudflare.com
```

Google's own guide asks for more than the review quoted. For **GA4**: `img-src` also
`https://www.googletagmanager.com https://*.google-analytics.com https://*.google.com
https://*.google.<TLD> https://*.g.doubleclick.net`; `connect-src` also
`https://www.googletagmanager.com` and the same three; `frame-src`
`https://www.googletagmanager.com`. For an **Ads conversion tag**: `script-src-elem` also
`https://www.googleadservices.com https://www.google.com`, plus img and connect hosts.

**Missing today:** `www.googletagmanager.com` in img-src and connect-src, `*.google.com`,
`*.g.doubleclick.net`, and `www.googletagmanager.com` in frame-src. **Every Ads host.**

**Root cause.** The policy was built from what the page was measured requesting, which
captured GA4's `region1.google-analytics.com` but not the image pings or the doubleclick
hosts, and could not capture an Ads tag that does not exist yet.

**Note for the fix.** `https://*.google.<TLD>` is a placeholder in Google's document, not
a literal. It cannot be written into a CSP as-is; the fix must name the TLDs we serve.

## E11 — consent cannot be withdrawn on the site (compliance)

The footer's "Cookies" link points at `/legal/cookies/`, which tells the visitor to
"borrar el almacenamiento local de este sitio en los ajustes de tu navegador". A search of
`frontend/src` finds no control that reopens the banner or clears the stored choice
anywhere outside `consent.tsx` itself.

**This is a compliance defect against a rule already verified in this repository**
(docs/verified.md, 18 Sep, AEPD *Guía sobre el uso de las cookies* MAYO 2024): withdrawal
must be as easy as giving consent. Giving it is two taps; withdrawing it is a trip into
browser settings.

## KNOWN-2 — the retry interaction, and why the stated failure mode is inverted

Measured:

```
Cloud Run timeoutSeconds : 300
infra/gcp.tf:118  max_attempts = 5
infra/gcp.tf:119  min_backoff  = "10s"
infra/gcp.tf:120  max_backoff  = "300s"
app/core.py:103   LEASE_SECONDS = 600
```

The queue sets no `dispatch_deadline`, so it takes the provider default.

`app/core.py:195-216` holds a lease: a second worker that finds `started_at` within
`LEASE_SECONDS` returns without generating, and `app/main.py` turns that into a 500 so
Cloud Tasks backs off.

**So the stated failure — five generations, twenty paid images — does not follow.** Work
it through: attempt 1 runs 0–300s and Cloud Run kills it. Retries arrive at roughly
t=310, 330, 370, 450 as the backoff doubles from 10s. Every one of them is inside the
600s lease, so every one returns 500 without generating. Attempts are exhausted at five.

**The real defect is the opposite: the order is never delivered at all.** The customer has
paid, the retries are spent bouncing off a lease held by a worker Cloud Run already
killed, and nothing ever generates. There is also a genuine atomicity gap — the claim is
read-then-write, not a transaction, so two simultaneous dispatches can both pass it — but
that is the smaller of the two problems.

**Fix.** An atomic claim (Firestore transaction, the pattern `OrderStore.claim_event`
already uses), and a lease shorter than the window the retries actually span so a dead
worker's order is picked up while attempts remain.
