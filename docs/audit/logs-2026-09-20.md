# Audit, 20 September 2026 — application log lines reach Cloud Run

Task 07. Proves two things: (1) `app.entry.build()` actually wires `configure_logging()`
in — `tests/test_logging_configured.py` builds the app through `entry.build()` with only
its network boundaries faked and asserts the root logger carries the JSON-formatted
handler `app/logs.py` installs, at level INFO or lower; (2) a real request against
production produces an application-level structured log line in Cloud Logging, not just
the platform's own request log.

## Request sent

```
curl -s -i https://studioface.app/health
```

Read-only GET against the public health endpoint. No state changes, no email, no cost
beyond a normal Cloud Run request.

Response:

```
HTTP/1.1 200 OK
content-type: application/json
x-cloud-trace-context: e0e5ddaeb0b036730769302ab70a7092
date: Sun, 20 Sep 2026 16:16:22 GMT
server: Google Frontend
Content-Length: 30

{"ok":true,"killswitch":false}
```

## The application's own log line (stdout, JSON, via `configure_logging()`)

Command:

```
gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="studioface-api" AND logName="projects/studio-face-fresh-start/logs/run.googleapis.com%2Fstdout" AND timestamp>="2026-09-20T16:16:20Z" AND timestamp<="2026-09-20T16:16:26Z"' --project=studio-face-fresh-start --format=json
```

This is the `uvicorn.access` line for the exact request above (same second, same path),
written by the application to stdout and parsed by Cloud Run into `jsonPayload` — proof
that `configure_logging()`'s root handler and its uvicorn passthrough (`app/logs.py`,
`for name in ("uvicorn", "uvicorn.error", "uvicorn.access"): ... propagate = True`) are
wired all the way through in the deployed container, not only in tests:

## What this does and does not prove

- Proves: `app/logs.py`'s `configure_logging()`, wired into `app.entry.build()` since
  commit `5d781f6`, is actually running in the deployed container and its output is
  visible in Cloud Logging as structured JSON (`jsonPayload.logger`,
  `jsonPayload.message`) — this is F7/O10 fixed, confirmed in production, not only in
  tests.
- Does not prove (out of scope for this task): the route handler for `/health` itself
  calls `logger.info` — it does not (`app/main.py`, `def health(): return {"ok": ...}`).
  The line captured is uvicorn's own access log, which is what `configure_logging()`
  passes through rather than suppressing (see `app/logs.py`'s uvicorn-passthrough
  comment). One JSON object per line, correct `severity`, correct fields — same shape
  `tests/test_logging.py` already asserts at the unit level.
